# CLAUDE.md — правила работы в репозитории ai-crm (NSTORE CRM)

Монорепо: `be/` (NestJS, Prisma 7, PostgreSQL, Redis) и `fe/` (Next.js App Router, next-intl, react-hook-form + zod, react-query, axios, sonner, shadcn/ui). Прод: backend на Railway, frontend на Vercel. Деплой и окружение описаны в `DEPLOYMENT.md`.

## Как работать

- Работай только в ветке, которую назвал пользователь. Не делай `git push`, не открывай PR, не меняй `main`.
- Один логический коммит на задачу, сообщение в стиле `fix(scope): ...`, `feat(scope): ...`, `chore(scope): ...`.
- Держи дифф минимальным: не переформатируй файлы целиком (в `fe/` prettier не настроен, файлы переводов `fe/messages/*.json` не форматируй, добавляй только новые ключи).
- Соблюдай блок «НЕ ТРОГАЙ» из задачи. Если для решения нужно выйти за рамки задачи, остановись и сообщи, а не делай сам.
- Временный код (комментарии `TEMP`, диагностические логи и эндпоинты) в коммиты не попадает, а если без него не обойтись, пометь и сообщи.
- В конце всегда честно напиши: что проверено, что не проверено (живую БД, Redis, Railway, браузер обычно проверить нельзя), какие допущения сделал.

## Проверки перед сдачей

В `be/`: `npx tsc --noEmit`, `npx eslint <изменённые пути>`, `npx prettier --check <изменённые пути>`, `npm test` (jest), `npm run build` (`nest build`), при изменении схемы `npx prisma validate` и `npx prisma generate`.
В `fe/`: `npx tsc --noEmit`, `npx eslint <изменённые пути>` и `npm run build` (`next build`), если менялись маршруты, `next.config.ts`, переводы или границы серверных и клиентских компонентов. Тестового раннера во фронте нет (скрипт `test` — заглушка), поэтому проверка фронта состоит из tsc, eslint и сборки.
Не запускай целиком `npm run lint` и `npm run format` в `be/`: `lint` вызывает eslint с `--fix`, а `format` переписывает все файлы в `src` и `test`, из-за чего дифф раздувается. Prettier настроен только в `be/` (`be/.prettierrc`), в `fe/` его нет, поэтому файлы фронта целиком не форматируй.
Новые ошибки недопустимы. Тесты на новое поведение пиши до реализации и убеждайся, что они падают без неё.

## База данных и миграции

- На боевой БД лежат данные клиента. Миграции только аддитивные (expand → switch → contract в разных релизах). Ничего не удаляй и не меняй в одной миграции с изменением кода.
- Миграции лежат в `be/prisma/migrations/<timestamp>_<name>/migration.sql`. Если БД в песочнице нет, пиши SQL вручную в стиле существующих и проверяй через `prisma validate`.
- Пуш в `main` запускает пайплайн: бэкап `pg_dump`, `prisma migrate deploy`, деплой.

## Мультитенантность и пользователи

- Prisma-расширение (`be/src/common/services/prisma.service.ts`) автоматически изолирует по `tenantId` только модели из `tenantModels` (User, Contact, Deal, Activity, Task, AiSuggestion, Invitation, KpiTarget, AuditLog, Channel, Message). `ChannelMember` и другие модели без `tenantId` не изолируются: id пользователей из запроса проверяй явно (`tenantId` и `deletedAt: null`).
- Вне HTTP-конвейера (gateway, worker) `tenantId` берётся из CLS: оборачивай в `cls.run` и задавай `tenantId`.
- Пользователи удаляются мягко (`User.deletedAt`). Во всех запросах, где выбираются, назначаются или проверяются пользователи, добавляй `deletedAt: null`. Не используй `prisma.user.delete()`.
- Роли в данных хранятся как `ADMIN` / `MANAGER` / `SALES_REP`. Отформатированные названия (`Admin`, `Manager`, `Sales Rep`) только для показа, не сравнивай с ними.

## Авторизация и лимиты

- JWT лежит в cookie `accessToken`; refresh-токены в Redis (`auth:refresh:<token>`, `auth:refresh:user:<userId>`) и в таблице `RefreshToken`. Отзыв доступа деактивированному делает `SessionRevocationService` (Redis denylist по `userId`). Не вызывай его там, где человеку нужно сразу снова войти (например, при сбросе пароля).
- Лимиты: общий 300 запросов за 60 с, `BRUTE_FORCE_GUARD_THROTTLE` 5 за 60 с на auth-эндпоинтах. Значения не повышай. Новые публичные эндпоинты, где можно перебирать пароли и токены, помечай `@Throttle(BRUTE_FORCE_GUARD_THROTTLE)`.
- IP клиента определяется в `ClientIpThrottlerGuard` (предпоследний элемент `X-Forwarded-For`), не используй `req.ip` для идентификации клиента: за прокси Railway это меняющийся адрес узла. `trust proxy` остаётся `1`.
- Публичные эндпоинты на бизнес-ошибки отвечают 400, а не 401: фронтовый axios-интерцептор (`fe/src/lib/api.ts`) на 401 запускает refresh и редирект на `/login`.
- Хранилище лимитов in-memory (одна реплика на Railway). При появлении нескольких реплик нужны Redis-хранилище throttler и Redis-адаптер Socket.IO.

## Ошибки, переводы, логи

- Бэкенд бросает `AppException` с кодом из enum в `be/src/common/errors/error-codes.ts`. Каждый новый код добавляй в раздел `errors` в `fe/messages/ru.json` и `en.json`: ключ равен значению enum (например, `AUTH_PASSWORD_SAME`).
- Языки интерфейса только `ru` и `en`, `localePrefix` всегда. Все строки добавляй в оба файла. Навигацию во фронте делай через `@/i18n/navigation` (`Link`, `useRouter`).
- Логи через `rootLogger` (pino), без `console.log`. Не логируй токены, пароли, ссылки сброса и целые объекты запроса. Стандартный уровень `info`, вход на `warn`, детали на `debug`.

## Фронтенд

- Не читай `localStorage` внутри `useState`-инициализатора (hydration mismatch): стартовое значение по умолчанию и чтение в `useEffect` после mount.
- Компоненты в `fe/src/components/ui` (shadcn/ui) не переписывай без необходимости; тосты через `sonner`; ошибки API через `useApiError`.

## Тесты

- Jest в `be/`. Пакет `@nestjs/event-emitter` ESM, в спеках на сервисы, которые его импортируют, мокай его локально (`jest.mock('@nestjs/event-emitter', ...)`), конфиг jest не менять без согласования.
- Для логики с Redis и Prisma в юнит-тестах используй моки или in-memory заглушки, но в отчёте оговаривай, что живое поведение не проверено.

## Известные ограничения (не чинить без отдельной задачи)

- Автоджойн комнат Socket.IO считается один раз при подключении; новые каналы требуют переподключения.
- «Прочитано X из Y» считается по текущим участникам канала, а не по составу на момент отправки.
- У деактивированного участника остаются контакты, задачи, активности и сообщения; открытый WebSocket не рвётся принудительно.
- Роль, на которой остались деактивированные участники, нельзя удалить.
